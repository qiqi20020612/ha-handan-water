# 协议审查（2026-10-19）

依据：用户提供的脱敏 JSON 六组请求/响应，以及原始抓包中的 HTTP 头、[21] 我的账单、[33] 缴费详情、[47] 交费记录、[56] 用水分析及 [22]/[50] util1.js。原始资料在仓库外分析；公开仓库只保存字段、语义和合成数值。真实读数、用量、金额、账单及交易日期不公开。第三方 Vue、jQuery、ECharts 和微信 SDK 不作为认证实现依据。

## 请求和认证

接口是 `http://www.hdwsc.com.cn/adsWeChat/pt.action`，POST `application/json`。四个查询均使用以下封装，`in_json` 是对象，不能再 JSON 编码为字符串：

```json
{"id":"4YA45Q","param":{"in_json":{"head":{"servCode":"200001","version":"1.0.1"},"body":{"queryType":"0","queryValue":"DEMO_ACCOUNT_001"}}}}
```

- 原始查询请求头无 Cookie、Authorization，JSON 无签名/时间戳/令牌。Origin/Referer 为网页来源，不是已证实的鉴权凭据。
- [16] 带 openid，[37] 及 [33] 页面实际的 200001 查询不带 openid；两份抓包都成功。其他三个业务查询也不带 openid。
- util1.js 的 `checkOpenid()` 检查 sessionStorage，关闭非微信入口页面；它没有给下面四个 AJAX 请求添加认证。页面绑定账户查询是另外的调用，不属于本集成。
- [38] 使用另一个路由 id、固定旧时间和机构头；它不是这四个查询的必要封装，不复制其中机构标识或旧头部。
- **抓包成功不能单独证明服务器在全新客户端中不需要其他认证。** UI 将用无 Cookie 的客户端实际验证户号。没有密码/openid 配置，也不模拟微信。
- 开发机不带户号的探测：HTTP GET 返回 405，HTTPS 连接超时（15 秒）。这只说明该次探测的结果，不能证明服务永久不支持 HTTPS。配置时先验证 HTTPS；仅在用户勾选明文风险同意后允许 HTTP 回退。TLS 证书校验保持开启，拒绝重定向。
- HTTP 会明文暴露户号及返回的姓名、地址等资料。本集成只取必要字段，不保留姓名、地址、电话、openid 或原始响应，不记录请求/响应或服务器错误文字。

### 独立客户端实测

2026-10-19，用户明确授权后，使用新建的 urllib 客户端分别发送 [37]/[27]/[52]/[58] 四个请求：无 Cookie、Authorization、openid、Origin、Referer 或微信 User-Agent，禁用重定向。四个 HTTP 查询均返回 200 / result=ok；200001/200008/200020 的 rtnCode=9999，200001 返回户号与请求匹配，200005 返回 12 张账单和 2 个不同水表，200008 返回 12 笔记录。响应只在内存检查，未保存真实账户响应。这验证了此户号在该时点/网络可脱离微信直接查询；不推论所有户号和未来鉴权策略均相同。

## 响应校验

封装是 `result == "ok"`、`data.head.servCode`、`data.body`。200001/200008/200020 的 `body.rtnCode == "9999"` 是成功；200001 的 `rtnMsg` 可以是“未欠费”，不能据此判为失败。200005 成功样本无 rtnCode，直接包含 `reclist`；若未来出现 rtnCode，也必须检查。拒绝不匹配服务码、缺失必需容器、无穷数/NaN、非法日期等结构变化，不能把损坏数据转换成零。

没有提供无效户号/认证过期的业务失败样本，**不臆造失败码与认证失败之间的映射**。HTTP 401/403 为认证拒绝；其他非 9999 业务码仅报固定业务错误，提示核对户号；200001 成功但 consNo 缺失/为空或不匹配视为户号无效。网络失败与空列表分开处理。

## 账户与水表

200001 的 `totalOweAmt` 是账户欠费，`prepayAmt` 是预存余额；`RecentPay` 被 [33] 页面显示为最近缴费。真实样本的 `RecentWater` 与两表当期合计不一致，不能当作账户总用水或赋给任一水表。`rceAmt/misaving` 在账单页分别显示欠费/余额，但本实现优先采用 200001 的明确账户字段。

200005 的每条 reclist 是一张水表账单：

| 字段 | 语义 |
| --- | --- |
| rlid | 账单标识，作为去重/修订检测依据，不暴露业务流水 |
| rlmcode | 真实水表编号，设备身份依据，绝不按数组位置分表 |
| rlscode / rlecode | 上次/本次累计读数，m³ |
| rlsl | 该抄表区间用量，m³；不能当作每日用量 |
| rlprdate / rlrdate | 真实起止抄表日期，YYYY/MM/DD，无时分秒 |
| rlmonth | 账务月份，不是实际抄表时间 |
| rlje | 账单应收金额（不等于实际缴费） |
| rlpaidflag | Y 为已缴，其他值不自动解释为具体付款动作 |
| rlznj | 此账单中的滞纳金字段，独立保留，不擅加进 rlje |
| recdetail | piname 项目、rddj 单价、rdsl 数量、rdje 分项金额 |

原始样本有 12 张账单、2 块水表、6 个账期。全部样本均满足止码减起码等于 rlsl；分项金额之和等于 rlje。历史中账单 rlznj 与付款 pznj 不总一致，不合并计算。公开合成示例最新账期为 2026.09：表 1 从 1025 到 1027、用量 2、应收 10；表 2 从 208 到 209、用量 1、应收 5。这些数字不代表任何真实账户或供水价格。

## 缴费与预存

200008 的 payment 为账户级交易，`pid` 去重，`pdatetime` 是 YYYYMMDDhhmmss（按供水所在地 Asia/Shanghai），`pmonth` 是账务月份。其内嵌销账 reclist **没有水表编号**，不能按行位置或金额匹配分摊至水表。

- `ppayment`：本次实交，含只增加预存的交易。
- `pspje`：本次应交/销账金额。
- `psavingqc` / `psavingqm`：期初/期末预存。
- `psavingbq`：预存净变动，是有符号值；负数表示动用预存，正数表示增加预存。网页虽然把它标作“抵扣预存”，样本不支持把正数也叫抵扣。
- `pznj`：本次交易滞纳金，独立保留。

真实样本的 12 笔均满足 `psavingqm = psavingqc + psavingbq` 及 `pspje = ppayment - psavingbq`。公开合成示例为实交 12、应交 15、预存变动 -3，即抵扣 3；两表 rlje 合计 15。纯预存交易 ppayment > 0、pspje = 0，不能计作水费应收。

## 用水分析

200020 的 `waterinfo2` 为 `YYYY.MM#用量|...|`；`waterinfo1` 为排名等混合的 `|` 分隔字段，`waterinfo3` 为空。样本趋势只匹配表 1，无法确认多表聚合规则。仅提供默认关闭的“网站用水分析”诊断实体，保留 waterinfo2 的解析趋势；不将其接入能源统计或声明为账户总用水，不暴露含标识的 waterinfo1。
